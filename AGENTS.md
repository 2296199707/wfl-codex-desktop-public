# WFL Codex Desktop Repository Rules

- Never disable, suspend, block, or revoke an administrator's ability to use conversations. Maintenance, deployment, recovery, and permission changes must preserve administrator conversation access; if a running task is interrupted, reconnect or recover it instead of banning or locking the conversation.
- Treat the rescue window as an independently frozen production component whose desired active rescue port is `4321`. Main-site releases, deployments, version synchronization, service-unit installation, rollback, recovery, pushes, and ordinary update requests must not change `rescue-active-port`, start/stop/restart/enable/disable a rescue service, rewrite a rescue slot symlink, replace rescue assets, or change its component version. Generic instructions such as "update", "deploy", "release", or "push" never authorize rescue-window changes. Change, switch, recover, or upgrade the rescue window only when the owner explicitly requests that specific rescue-window action in the current request. When the owner explicitly requests a rescue-window upgrade, increment the rescue component version from its current version, update its own asset cache keys and package metadata consistently, verify the inactive slot, switch safely to `4321`, and then freeze that new version; never reuse or reduce a rescue component version.
- Never run complete repository test suites, load/stress tests, or browser smoke tests while installing or synchronizing a formal release on an ordinary user's server. Ordinary servers may run only bounded compatibility checks and post-deployment health/readiness verification. Complete suites must run on the primary development or candidate-release server before the formal package is published, unless the owner explicitly requests a diagnostic test on a specific server in the current request.
- Every main-site deployment must use a new version and the existing blue-green path: start and verify the candidate, switch and verify traffic, then stop the old backend. Never deploy different code under the same version or invent an alternate deployment path.
- Owner's durable deployment preference (recorded 2026-08-14): for a main-site or official Codex update, use an immediate forced switch by default and do not wait for active tasks to become idle, unless the owner explicitly asks for a waiting/safe-drain update for that operation. A forced switch still must use a new version, the existing blue-green candidate path, deployment watchdog, readiness checks, writer fencing, and recovery; it must not bypass validation or touch the frozen rescue window.
- Keep third-party subagent behavior and settings aligned with the current official OpenAI Codex subagent design. Do not expose or enforce WFL-specific task budgets, continuation states, lifecycle controls, roles, or orchestration policies. Any subagent design that is not established by the official design requires the owner's explicit approval before implementation.
