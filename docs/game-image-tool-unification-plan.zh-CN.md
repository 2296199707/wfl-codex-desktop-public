这三个目录是本次检查中的样本，职责不同，但它们都不是协议里写死的工程路径。后续讨论和测试必须明确写出目标目录：

| `/srv/wflgame` | 已有游戏项目/编辑器参考工程样本 | 当前已有 `src`、`maps`、`assets`、`dist` 和游戏测试，可用于复现编辑器行为；不是所有新游戏的默认目标 |

此前检查的 `/srv/wflgame/maps/city/cloud_gate_plaza.tmj` 属于参考工程。关于“没有瓦片层”“没有 `.tiled-project`”的结论只对
`/srv/wflgame` 当前文件成立，不代表当前新工程已经选择了地图结构；本次样本目录 `/srv/aigame` 目前还没有可供检查的游戏地图。

后续规则：

- WFL 功能代码继续在 `/srv/wfl-codex-desktop` 修改；
- 新游戏的 `.tiled-project`、地图、建筑素材和资源目录创建到用户当前选择的、服务端已授权的 `projectPath`；本次可以选择 `/srv/aigame`，但代码和协议不得特殊处理这个路径；
- `/srv/wflgame` 只作为现有工程兼容性和编辑器回归参考，除非明确指定，不向其中写入新游戏内容；

- 自动化测试使用测试自己创建的临时工程根，不把任何真实游戏目录当作测试夹具，也不把测试文件写入真实游戏目录。

## 1. 结论

当前问题不是单个编辑器坏了，而是三个层次的入口和上下文混在了一起：

1. 通用文件管理器负责浏览任意目录和文件操作；
2. 游戏工作区负责一个已确认的游戏工程，以及地图、World、瓦片集、角色和游戏素材；
3. 图片工作室负责通用图片生成、编辑和扩图；地图编辑器还有一个绑定地图版本的图片候选发布流程。

建议采用以下稳定结构：

```text
工具箱
├── 资源管理器       通用文件浏览、上传、下载和预览
├── 游戏工作区       一个游戏工程内的全部游戏编辑能力
│   ├── 资源
│   ├── 地图
│   ├── World
│   ├── 瓦片集
│   ├── 角色
│   ├── 图片/素材
│   └── 预览
├── 图片工作室       通用图片生成、编辑和扩图
└── 浏览器预览       游戏或网页入口预览
```

地图编辑器、World 编辑器、瓦片集编辑器和角色动作编辑器不再作为工具箱的并列一级入口，而是游戏工作区里的
上下文编辑器。图片工作室仍可作为独立工具打开，但游戏工作区和资源管理器打开图片时必须调用同一套图片工作室
实现，不能再维护第二套图片编辑入口。

这不是把所有功能删掉，而是把入口从“按内部模块分散”改成“按用户任务分组”。现有后端服务、地图事务、图片候选
任务和旧 URL 可以先保留，待新入口验证后再清理兼容层。

又重复展示地图、World、瓦片集和角色入口。资源管理器的文件预览还会根据文件类型提供地图编辑器、图片工作室和视觉审查等

### 2.2 入口合并规则

| 用户动作 | 唯一主入口 | 允许的快捷入口 | 不再保留 |
| --- | --- | --- | --- |
| 浏览服务器文件 | 资源管理器 | 文件预览中的通用打开 | 单独的“游戏资源”一级卡 |
| 编辑地图 | 游戏工作区 -> 地图 | 资源管理器对 `.tmj` 的“在游戏工作区打开” | 工具箱一级“地图编辑器”卡 |
| 编辑 World | 游戏工作区 -> World | 资源管理器对 `.world` 的上下文打开 | 与游戏工作区并列的 World 入口 |
| 编辑瓦片集 | 游戏工作区 -> 瓦片集 | 资源管理器对 `.tsx/.tsj` 的上下文打开 | 与游戏工作区并列的瓦片集入口 |
| 编辑角色 | 游戏工作区 -> 角色 | 资源管理器对角色文件的上下文打开 | 工具箱一级“角色动作编辑器”卡 |
| 处理普通图片 | 图片工作室 | 从已选图片打开并带入源图 | 角色编辑器或资源管理器自建图片编辑 UI |
| 生成地图素材 | 游戏工作区 -> 地图 -> 地图素材候选 | 地图选区、图片层或当前地图资源动作 | 把地图图片任务当作第二个通用图片服务 |
| 运行游戏或网页 | 浏览器预览 | 游戏工作区 -> 预览 | 再增加项目级预览入口 |

资源管理器仍可访问任意目录，这是上一项单用户功能的要求。但“能访问文件”不等于“这个文件就是当前游戏工程
资源”，两者必须在界面和协议上明确区分。

## 3. 工作路径问题

### 3.1 已发现的多套路径来源

当前专业工具同时使用以下来源：

- URL hash 中的 `project`、`projectFile`、`path`、`source`；
- `currentProject`、`resourcePreviewEntry`、`mapWorkspaceSelectedEntry` 等主界面状态；
- `localStorage` 或 `sessionStorage` 中的上次工程；
- 地图编辑器自己的 `MapProjectWorkspaceClient`；
- 地图会话返回的 `projectSessionId`、`relativePath` 和版本；
- 图片工作室要求的绝对 `project` 加工程相对 `sourcePaths`；
- AI 图片工具要求模型直接携带绝对 `project`；
- World 和瓦片集编辑器仍从 hash 读取绝对工程路径。

这些来源可能分别指向不同工程。最典型的错误链是：主界面打开项目 A，角色编辑器从 localStorage 恢复项目 B，
图片工作室再从当前全局项目或资源预览状态取源图，最终出现“编辑器显示一个工程、请求写入另一个工程”的风险。

### 3.2 现有会话并非完全重复

地图编辑器目前有两个有意义但层级不同的会话：

- 地图会话：绑定具体 `.tmj`、版本、编辑器实例、账号和地图 AI 租约；
- 项目工作区会话：绑定工程根、工程文件和工程内相对资源。

`MapProjectWorkspaceClient` 在 `public/map-project-session.js:48-193` 定义了工程会话；地图、World 和瓦片集服务分别在
`server.mjs:19013`、`19527`、`19842`、`19945` 附近建立资源会话。它们不能简单删除其中一个，否则会丢失地图版本冲突、
工程引用校验或 Tiled 资源读取能力。

真正需要消除的是客户端的重复推断：地图编辑器启动后又根据 `state.credentials.projectPath` 建立一套隐含工程绑定，
而角色编辑器还允许自己的工程列表、输入框和记忆工程覆盖主界面传入的工程。

## 4. 统一上下文协议

后续所有游戏编辑器、图片工作室和 AI 入口都应围绕一个明确的 `projectContext` 工作。首版可以继续映射到现有地图
会话和工程会话，不要求一次重写所有后端路由。

建议的逻辑结构：

```js
{
  projectId,         // WFL 持久工程记录 ID，不由目录名推导
  projectPath,       // 仅服务端确认；不由 AI 自由指定
  projectFile,       // 工程相对路径，例如 .tiled-project
  relativePath,      // 当前资源相对工程根的路径
  resourceKind,      // map | world | tileset | character | image
  projectSessionId,  // 工程资源会话
  editorSessionId,   // 当前编辑会话，可对应现有 mapSessionId
  editorInstanceId,  // 当前窗口/标签实例
  hostWindowId,      // 发起该编辑器的主窗口
  threadId,          // 当前工程绑定的 AI 对话；不能被打开编辑器的外层对话覆盖
  accessMode,        // editor | ai-read | ai-bound；ai-read 只读，ai-bound 允许修改
  accountId,         // 账号隔离
  version            // 当前资源或地图的服务端版本
}
```

约束如下：

1. 主站先选择工程，再由服务端创建或复用工程会话，返回规范化的上下文；子编辑器只接收会话 ID 和当前资源的相对路径。
2. `projectPath` 是服务端会话的结果，不是模型、URL 或子编辑器输入的权威来源。为兼容旧链接可以暂时接受旧参数，
   但打开后必须以服务端返回值覆盖，不能继续使用旧值。
3. `projectFile`、`relativePath`、地图引用和图片源路径均以工程相对路径表示，并由服务端按会话重新解析和校验。
4. 编辑器打开后只信任服务端返回的 `projectContext`，不再从 `currentProject`、资源预览项、localStorage 或旧窗口状态
   二次推断工程。
5. 切换工程、资源或账号时生成新的上下文代数/会话，旧编辑器的读写请求必须因会话或版本不匹配而停止，不能继续使用新工程路径。
6. `resourceKind` 是必填语义字段。不能仅凭文件扩展名或一个模糊的 `source` 参数决定进入哪种编辑器。
7. 图片工作室的通用请求也只接收上下文引用和工程相对源路径；AI 不应直接传入任意绝对工程目录。
8. 人工编辑器的打开、查看和操作不由 AI 绑定限制；有工程访问权限的任何 AI 对话都可以读取工程，只有修改能力同时受“一个对话只绑定一个工程”和“一个工程只绑定一个对话”约束。
9. 从任何窗口打开游戏编辑器时，右侧 AI 小窗都从服务端解析该工程的已绑定 `threadId`；打开编辑器的外层对话不能覆盖这个绑定。

### 4.1 单用户任意目录边界

资源管理器现在允许单用户访问任意绝对目录。这个能力必须继续保留，但边界要固定为：

- 外部目录可以浏览、上传、下载、预览和进行通用文件操作；
- 外部目录中的绝对路径不能自动变成游戏工程 `projectPath`；
- 地图、World、瓦片集、角色和地图图片候选等专业工具只接受经过服务端确认的游戏工程会话；
- 当前已经对外部目录隐藏专业编辑按钮的行为应继续保留，不能为了“入口统一”而把任意目录文件直接送进游戏编辑器；
- 如果未来要让普通图片工作室处理外部图片，应单独设计通用资源会话，不复用游戏工程上下文。

## 5. 推荐的界面结构

### 5.1 工具箱一级入口

一级只保留四项：

1. `资源管理器`：服务器文件系统，允许任意目录；
2. `游戏工作区`：必须先选定一个游戏工程；
3. `图片工作室`：通用图片操作，可选带入当前工程图片；
4. `浏览器预览`：选择当前工程的 HTML 入口。

删除的是重复的一级卡，不是编辑功能。游戏工作区内部使用标签或分段导航：`资源`、`地图`、`World`、`瓦片集`、`角色`、
`图片/素材`、`预览`。当前上下文固定显示在工作区标题栏：

```text
游戏工作区
工程：Forest Game
当前资源：maps/forest.tmj
会话：已连接 · 可编辑

资源 | 地图 | World | 瓦片集 | 角色 | 图片/素材 | 预览
```

游戏工作区的资源树只显示当前工程资源，不替代资源管理器的任意目录浏览。

### 5.2 专业编辑器打开规则

- 从游戏工作区打开：直接使用工作区的 `projectContext`；
- 从资源管理器打开：先请求服务端把所选文件解析成游戏工程上下文，成功后跳转游戏工作区或其子编辑器；
- 从图片工作室打开：使用同一个 `projectContext`，只增加 `resourceKind: image` 和 `relativePath`；
- 从角色编辑器打开图片工作室：沿用角色编辑器当前上下文，源图只能来自该工程会话；
- 地图编辑器里的图片对话框：继续绑定地图会话、地图版本和选区/图片层，但界面名称改为“地图素材候选”，明确它是
  地图工作流中的候选任务，不是另一套图片工作室。

所有入口最终都走一个“打开上下文资源”的主函数。不能继续让每个入口自己拼 URL、自己选择工程、自己恢复路径。

### 5.3 新建游戏工程

游戏工作区的空状态和工程选择区域增加唯一的“新建游戏工程”按钮。新建流程必须面向任意已授权目录，不能把
`/srv/aigame` 或任何其他路径写入代码。

向导只要求用户确认真正影响初始结构的内容，默认值可以修改，但不把供应商、Tiled 或 WFL 的所有高级参数一次性铺开。
向导中的选项全部是“初始化预设”，不是进入工程后的固定模式、权限开关或隐藏上限；工程打开后仍应在工程设置、地图设置
和编辑器中修改。需要转换已有数据的设置，必须提供明确的转换/确认流程，不能因为实现方便就永久锁死。

1. **位置和名称**：选择工程目录、工程名称和初始地图文件名。服务端检查目录可访问、目录不存在冲突；非空目录不静默覆盖，
   需要另行走导入/打开已有工程流程。
2. **地图工作模式预设**：默认推荐“建筑/经营地图”，另提供“背景图 + 对象地图”。这里决定初始创建哪些层，不锁定工程今后的
   编辑方式；用户进入后仍可添加、删除和调整瓦片层、图片层及对象层。
   - 建筑/经营地图创建空白 Ground 瓦片层，并创建 Buildings、Collision、Events 等对象层；适合自由摆放建筑、碰撞和事件。
   - 背景图 + 对象地图创建 Background 图片层和对象层；适合现有整图背景，不宣称支持瓦片画笔。
3. **基础地图参数预设**：地图方向、宽高、瓦片宽高和初始资源来源。参数由用户确认，使用正常格式校验，不增加一套隐藏的
   WFL 固定上限。进入工程后仍可修改；如果修改会影响已有数据，应提供保留原文件、转换副本或明确确认的选项。选择建筑/经营
   模式但未提供瓦片集时，应明确提示“先添加瓦片集后才能使用瓦片工具”，不能让用户误以为编辑器损坏。
4. **工程资源骨架预设**：创建 `.tiled-project` 和标准资源目录，例如 `maps`、`assets/tilesets`、`assets/buildings`、
   `assets/characters`、`assets/generated`、`docs`；目录名作为模板配置可调整，不要求所有工程必须使用同一套名称。创建这些
   目录不限制用户后来增加、移动或使用其他资源目录。
5. **可选入口设置**：如果用户已经提供 HTML 入口或初始瓦片集，则一并登记；没有时保持未设置，不阻止工程创建。

创建成功后，服务端一次性返回新的 `projectContext`，包括工程会话、工程文件、初始地图和版本基线，工作区自动打开
该上下文，并登记一个持久的“我的游戏工作区”入口。后续地图、World、瓦片集、角色、图片和 AI 请求都从这个上下文派生，
不再重新询问或推断路径。

新建操作应先在临时位置生成并完成结构校验，再一次性落到目标目录；失败时不能留下半套工程。完成页只显示实际创建的文件、
当前地图模式和可用工具，不把“已创建目录”误报成“已准备好完整编辑环境”。

### 5.4 已创建工程和工作环境恢复

工具箱在游戏工作区入口下增加“我的游戏工作区”列表。每个工程条目是 WFL 管理的持久记录，不是一个简单的前端路径书签：

```text
我的游戏工作区
├── Forest Game       最近打开：maps/forest.tmj · 可编辑
├── Cloud Prototype   最近打开：maps/cloud.tmj · 只读/需检查
└── 新建游戏工程
```

新建向导中的“工程名称”是用户可见的显示名称。它可以和目录名不同，之后也可以重命名；真正用于打开工程的是稳定的
`projectId`，不能用名称或目录名作为唯一键。这样即使存在同名工程，也能通过副标题显示位置和最近打开资源来区分。

工程记录至少包含：

- 不依赖目录名称的 `projectId`；
- 用户设置的工程显示名称；
- 用户选择并经服务端确认的工程位置；
- 工程显示名、`projectFile` 和工程指纹/状态；
- 最近打开的资源、编辑器类型、地图/World/瓦片集标签和最后一次已保存版本；
- 可恢复的界面状态，例如活动标签、面板状态、缩放和视口。

点击条目时，服务端先用 `projectId` 检查工程仍存在且当前用户仍有权访问，再创建新的工程会话和 `projectContext`，然后恢复
上次已保存的工作环境。前端不能把记录中的绝对路径直接当作编辑器授权，也不能因为工程不存在就静默切换到另一个工程。

恢复规则：

1. 创建完成页提供“进入游戏工作区”，同时把工程加入列表；关闭工具后，用户可从该列表直接返回，不需要再次填写路径。
2. 上次资源仍存在时，恢复到上次资源和编辑器；资源被移动或删除时，进入当前工程并显示明确的资源失效状态，不从其他项目寻找同名文件。
3. 上次地图、World 或瓦片集版本已变化时，先重新建立当前会话并显示版本状态，不能套用旧工程路径或旧版本缓存。
4. 关闭时存在未保存修改，必须先提示保存、放弃或取消关闭；“恢复上次环境”只恢复已保存上下文，不把未保存内容伪装成已保存结果。
5. 从列表移除工程只移除 WFL 的入口记录，不删除工程目录；删除真实文件必须继续走资源管理器的明确删除操作。
6. 列表和恢复记录按账号/单用户实例隔离；不会把一个用户的工程路径或最近资源暴露给另一个用户。

工程列表可以同时保留多个最近项目和收藏项目，不设置“只能保留一个当前工程”的隐式规则。清理策略只清理入口记录和
工作区快照，不清理用户工程文件；列表数量、排序和清理策略应是可调整的产品设置，不应成为编辑器能否打开工程的隐式限制。

### 5.5 缓存与快照分层

“缓存”和“快照”用途不同，不能混为一个数据源：

| 层级 | 保存内容 | 用途 | 权威性 |
| --- | --- | --- | --- |
| 工程注册表 | `projectId`、显示名称、服务端确认的位置、工程文件和指纹 | 让用户下次按名称找到多个工程 | 只负责定位，不代表文件内容 |
| 工作区快照 | `projectId + threadId` 对应的最近资源、编辑器类型、标签、面板、缩放、视口和最后已保存版本 | 恢复该对话在该工程中的工作环境 | 只负责恢复界面，不能直接写文件 |
| 工程索引缓存 | 工程相对文件清单、地图摘要、瓦片集摘要和缩略图索引 | 减少重复扫描，加快列表和资源树显示 | 必须带指纹/修改时间，过期后重建 |
| 显式工程快照 | 用户明确要求保存的工程文件副本或恢复点 | 发生误操作时恢复工程 | 作为备份副本，不替代当前工程 |

默认不把完整工程文件复制到浏览器缓存，也不把缓存内容当作编辑器的真实数据。点击工程名称时可以先显示工作区快照的
骨架，但在标记“已就绪”或允许写入之前，服务端必须重新确认工程存在、工程文件、当前版本和用户权限；检测到变化就刷新
索引并显示状态。

创建工程后立即生成注册表记录和当前对话的第一份工作区快照；每次明确保存成功后更新对应的 `projectId + threadId` 快照。
关闭工具时只保存界面状态，不能把未保存编辑标记成已保存。缓存失效、工程被移动或目录暂时不可用时，工程名称仍可保留
在列表中，并提供“重新定位/移除入口”，不能静默切换到另一个同名工程。

多个工程可以同时保留；每个对话同一时间只绑定一个工程。一个工程可以被多个不同对话使用，但同一个 `threadId` 不能
同时成为多个工程的 AI 写入上下文。

在对话中从工程 A 打开工程 B 时，执行一次明确的“解除 A 并绑定 B”：

- 先处理 A 的未保存修改，再停止或挂起 A 的编辑会话；
- 将当前对话的工程绑定从 A 替换为 B，重新建立 B 的 `projectContext`；
- 向 AI 发送明确的工程切换标记，后续工具只能操作 B；历史消息可以保留，但不能把 A 的路径、资源或授权带入 B；
- A 的工程记录和工作区快照继续保留，之后可以再次解除 B、重新绑定 A；
- 同一对话在多个窗口打开时共享同一个当前工程绑定，不能让不同窗口分别把同一对话指向 A、B；如果需要同时处理两个工程，
  使用两个对话。

绑定记录可以直接采用 `threadId -> projectId` 的简单关系，并附带账号、绑定时间和最后确认的工程指纹。AI 不能自行提交另一个
`projectId` 切换目标；解除绑定、绑定新工程和重新签发上下文都由主站工作区执行。

### 5.6 AI 对话绑定与编辑器入口

人工编辑器的打开、查看和操作不受 AI 绑定限制；AI 读取也不受绑定限制，但仍必须通过服务端工程访问权限和只读上下文。只有 AI 修改能力由工程绑定的对话提供：

| 能力 | 规则 |
| --- | --- |
| 人工打开、查看和操作游戏编辑器 | 当前用户有权限即可，不要求 AI 对话绑定 |
| AI 读取工程、地图、图片和资源 | 任何有该工程访问权限的 AI 对话都可以读取，不要求绑定 |
| AI 修改工程 | 必须使用同一条工程绑定的 AI 对话 |
| 一个对话绑定多个工程 | 不允许；先解除当前工程，再绑定另一个工程 |
| 一个工程绑定多个对话 | 只允许一个对话拥有修改绑定；其他有权限的对话仍可使用 AI 读取能力 |

工程注册表维护简单的一对一修改/AI 绑定：

```text
threadId  <->  projectId
```

绑定不是人工编辑器锁。任何窗口都可以打开同一个工程进行人工查看或操作；任何有权限的 AI 对话都可以读取该工程，
只有修改类 AI 工具必须解析该工程唯一的绑定对话。右侧 AI 小窗另有上下文规则，始终显示工程绑定对话。

从任意窗口打开游戏编辑器时，右侧 AI 小窗按以下顺序处理：

1. 根据当前工程 `projectId` 向服务端查询已绑定的 `threadId`；
2. 已绑定时，直接显示该对话的消息和状态，不能使用打开编辑器的外层对话替换它；
3. 未绑定时显示“绑定当前对话”，不创建没有工程归属的 AI 小窗；
4. 用户明确解除旧绑定并绑定当前对话后，所有打开该工程的编辑器窗口刷新到新的绑定对话。

如果用户在对话 A 中打开已绑定对话 B 的工程，工程编辑器仍可人工使用，但右侧 AI 小窗显示 B。要让 A 的 AI 参与，必须
先解除 B，再把 A 绑定到该工程。A 和 B 的聊天历史不会合并，工程路径也不会因为打开来源自动切换。

同一对话的多个编辑器窗口共享同一个绑定 AI 小窗；编辑器自身仍使用现有版本/哈希校验，防止多个标签页用旧内容覆盖新内容。
绑定转移只改变 AI 读取和修改权限，不删除文件、不禁用原对话，也不阻止原对话继续聊天或人工查看工程。

### 5.7 AI 小窗与主站对话同步

游戏编辑器右侧的 AI 小窗不是新的对话、摘要对话或独立的 AI 客户端，而是主站绑定对话的另一个视图。它与主站必须使用
同一个 `threadId` 和同一套对话服务：

- 主站对话存储是唯一权威来源，小窗不单独保存消息历史、提示词拼接结果或 AI 上下文副本；
- 小窗打开时从主站读取该 `threadId` 的权威对话投影，包括消息、附件引用、上下文管理状态、压缩摘要/compaction item、
  任务状态和工具活动摘要；不能在小窗自行拼接第二套上文。首版小窗先读取最近的有界 turns，较早记录由主站历史分页按需处理，
  这不会把“最近历史已就绪”误报成整条 Thread 已完整读取；
- 主站发送的消息、模型回复、工具调用、工具结果、失败、取消和完成状态都实时同步到小窗；小窗发送的消息也进入主站同一条对话，
  主站对话页必须能看到；
- 主站和小窗的停止按钮操作同一个活动任务和同一个 turn，不得各自启动或取消另一份请求；
- 小窗使用主站该对话当前的模型、供应商、设置和上下文状态，不复制一套局部设置；
- 多个编辑器窗口中的小窗都是同一对话视图，使用事件序号/游标去重，重连时从最后游标继续，不重复加载或重复发送；
- 发送请求使用主站现有的对话提交和幂等机制，小窗不能直接调用供应商 API 或另起一套任务队列；
- 工程绑定变化时，先停止订阅旧 `threadId`，清空旧工程视图，再订阅新绑定对话，不能把 A 的历史显示在 B 的小窗里。

从外层对话 X 打开已经绑定对话 Y 的工程时，外层页面可以继续显示 X 的主站对话，但游戏编辑器右侧小窗必须显示并同步 Y。
只有在明确解除 Y、绑定 X 后，小窗才切换到 X。工程没有绑定对话时，小窗只显示绑定入口，不生成临时会话。

主站和小窗的初次加载采用“元数据 + 有界历史页 + 增量事件”模式：小窗通过 `thread/read(includeTurns:false)` 获取元数据，
再通过 `thread/turns/list(itemsView:"full")` 获取最近历史页；加载期间收到的实时事件合并到同一 Thread 投影。按
`projectPath + threadId` 去重 hydration，多个编辑器窗口共享同一个读取请求；不会调用 `thread/resume`、切换主站当前对话或
创建临时 Thread。刷新按钮才显式重新读取；读取失败时保留已有缓存并显示错误，不清空可用消息。对话恢复、长任务、停止命令和错误状态
继续沿用主站已有的权威状态，不另设一套小窗任务状态机。

### 5.8 当前实施状态

已完成的阶段性部分：

- [x] 小窗显示工程绑定 Thread，而不是打开编辑器的外层对话；主站与小窗共享同一 `threadId`。
- [x] 非主站当前 Thread 也能通过只读 `thread/read` + `thread/turns/list` 显示最近消息。
- [x] 同一个 `projectPath + threadId` 的并发 hydration 去重；多个编辑器窗口共享结果。
- [x] hydration 返回期间合并已收到的事件，防止旧历史读取覆盖实时事件。
- [x] hydration 不调用 `thread/resume`、不调用 `selectThread`，不会改变主站当前对话。
- [x] 停止请求继续携带点击瞬间的 `threadId + turnId`，与历史读取相互独立。

尚未实施的较大范围：工程注册表、通用 `projectContext` 后端协议、新建游戏工程向导、工作区快照恢复和入口合并。这些仍按本文方案
单独排期，不在本轮借机重写，避免再次引入对话恢复链路的长等待。

## 6. 图片能力的统一边界

### 6.1 保留一个通用图片实现

`public/image-studio.js` 当前支持 `generate`、`edit`、`outpaint`，请求 `/api/images/v2/execute`，适合作为唯一通用
图片工作室实现。工具中心、资源管理器和角色编辑器都应调用它，而不是复制 UI 或请求拼装逻辑。

通用图片工作室负责：

- 生成一张或多张工程图片；
- 编辑已有工程图片；
- 扩图或裁剪；
- 结果预览、保存/附加和任务状态。

它不负责修改地图 JSON、改变瓦片层或自动把图片加入地图。

### 6.2 地图图片流程必须保留

地图编辑器图片流程依赖地图会话和地图版本，支持当前地图选区、图片层、临时输入、候选任务、候选发布，以及发布到
图片层、瓦片对象、瓦片集或伴随文件。这部分调用 `/api/maps/sessions/:sessionId/image-jobs`，不能粗暴替换成通用
`/api/images/v2/execute`。

统一方式是统一入口和上下文，而不是统一后端任务：

```text
图片工作室：生成/编辑/扩图 -> 工程图片结果
地图素材候选：地图选区/图片层 -> 带地图版本的候选 -> 明确发布到地图或瓦片集
```

供应商返回尺寸与请求参数不一致时，不能因为结果尺寸不同就拒绝结果。请求参数可按用户选择的模式传给供应商，返回图
片是否适合当前地图由用户在候选发布阶段决定。统一入口不应新增一套图片尺寸硬限制，也不应重复供应商已有的限制。

## 7. AI 暴露能力整理

当前 AI 能力按三个范围分组即可，不需要继续增加同义工具：

### 7.1 当前地图窗口协作

来源：`scripts/map-ai-mcp.mjs` 和 `lib/map-ai-tool-service.mjs`。

- `get_map_context`：读取当前已授权地图窗口的有限上下文；
- `propose_tiled_patch`：提交结构化补丁提案，供编辑器预览和用户确认。

这组能力依赖当前编辑器窗口、地图会话、编辑器实例和编辑器状态，适合“帮我看当前打开的地图”。它不应接收工程
绝对路径、图片字节或内部租约字段。

### 7.2 已授权工程协作

来源：`scripts/map-ai-managed-mcp.mjs` 和 `lib/map-ai-managed-tool-service.mjs`。

能力按用户意图分为四组，不要按内部路由把十几个操作平铺成一串：

| 分组 | 能力 |
| --- | --- |
| 查看 | `inspect_project`、`get_project_context`、`read_project_resource`、`get_map_context`、`read_map_region` |
| 校验与历史 | `validate_map`、`request_map_preview`、`list_map_revisions`、`restore_map_revision` |
| 生成提案 | `propose_tiled_patch`、`propose_project_patch`、`propose_tiled_resource_patch` |
| 应用已确认变更 | `apply_tiled_patch`、`apply_project_patch`、`apply_tiled_resource_patch` |

这里的 `propose` 只产生可审阅候选，`apply` 才创建持久化任务；二者的差异必须在工具描述中明确。应用操作继续受
授权、版本校验、候选 ID、原子保存、冲突检测和审计约束。

当前窗口协作和已授权工程协作都有 `get_map_context`、`propose_tiled_patch` 同名语义。稳定迁移策略是：

1. 先在工具描述、服务说明和 UI 中明确作用域；
2. 新调用统一优先使用“当前地图”或“已授权工程”的唯一目录；
3. 旧 MCP 工具名暂时保留为兼容适配，不再新增第三个同义工具；
4. 待调用方迁移并验证后，再移除重复的模型可见入口，不能先删除后端操作。

### 7.3 图片能力

来源：`scripts/image-provider-mcp.mjs` 和 `lib/image-provider-tool-service.mjs`。

保留 `generate_image`、`edit_image`、`outpaint_image` 三个清晰操作，但把工程绑定从模型提供绝对 `project` 改为已授权
的 `projectContext`/工程会话引用，源图继续使用工程相对路径。地图内生图仍由地图图片候选流程负责，不再同时向模型
暴露一个“通用图片写入地图”和一个“地图图片写入地图”的重复入口。

图片请求的参数模式（例如透传、部分透传、供应商默认）属于用户/管理员配置，不在这次入口整理中新增固定限制。统一的是
上下文和结果归属，不是把供应商参数重新封装成一套更严格的 WFL 参数表。

### 7.4 AI 不应看到的内容

无论是哪一组 MCP，都不向模型开放：

- 任意绝对工程路径或任意服务器路径；
- API Key、内部租约 token、文件句柄和临时上传字节；
- 通过参数绕过当前授权切换工程、地图或账号；
- 没有明确上下文的“当前项目”隐式写入。

这是上下文隔离，不是减少用户已经授权的游戏编辑能力。授权范围内的查看、提案、校验、预览、历史和应用能力仍应完整
暴露，只是用清晰的范围和生命周期表达。

## 8. 最小稳定实施顺序

### 阶段 0：只建立契约

- 增加并记录 `projectContext` 的规范化结构；
- 确定服务端返回的工程根、工程文件、相对资源和版本为唯一权威；
- 为旧 URL 参数保留兼容解析，但增加日志/诊断，找出仍在二次推断路径的调用点；
- 不改地图保存、图片 Worker、MCP 操作和资源管理器任意目录能力。

### 阶段 1：合并入口

- 工具箱移除地图编辑器、角色动作编辑器和游戏资源的一级重复卡；
- 增加一个游戏工作区，内部承载地图、World、瓦片集、角色、图片/素材和预览；
- 在游戏工作区空状态增加“新建游戏工程”向导，创建 `.tiled-project`、初始地图、资源骨架和首个 `projectContext`；
- 新建完成后登记带用户显示名称的“我的游戏工作区”入口，支持同时保留多个工程，并按 `projectId` 恢复最近的已保存工作环境；
- 资源管理器专业快捷按钮统一改为“在游戏工作区打开”；
- 通用图片快捷按钮统一调用 `openImageStudio`；
- 保留旧页面 URL，让已经打开的窗口可以继续工作。

### 阶段 2：收回路径控制权

- 主站创建/复用工程会话并生成 `projectContext`；
- 工程列表保存工程注册表和工作区快照，点击名称时按 `projectId` 重新建立服务端会话，不把缓存绝对路径当授权；
- 工程索引缓存仅用于加速，必须通过工程指纹或修改时间失效，不得覆盖磁盘上的最新内容；
- 地图、World、瓦片集和角色编辑器改为消费上下文，不自行从 localStorage、`currentProject` 或 hash 推断工程；
- 图片工作室请求从上下文解析工程，不再把模型传来的绝对路径当权威；
- 一个对话同一时间只绑定一个工程，支持先解除当前绑定再绑定另一个工程；
- AI 读取可使用当前用户有权限访问的工程只读上下文，不要求工程绑定；AI 修改必须使用工程绑定对话；人工从任何窗口打开游戏编辑器不受该绑定限制；
- 游戏编辑器右侧 AI 小窗始终解析工程当前绑定的对话，不使用打开编辑器的外层对话覆盖绑定；
- 资源切换时显式刷新上下文，旧版本请求继续返回冲突或会话失效，不允许静默写入新工程。

### 阶段 3：整理 AI 目录

- 为当前地图、已授权工程和图片能力增加明确的 MCP 分组说明；
- 在不破坏旧调用的前提下去掉模型可见的同义重复项；
- 将图片工具和地图素材候选的边界写入工具描述；
- 把 AI 的工程绑定改为授权上下文引用，继续禁止绝对路径和内部凭据。

### 阶段 4：清理兼容层

只有阶段 1 到 3 的验收通过后，才删除不再使用的一级入口、重复 UI 和旧参数分支。后端地图会话、图片候选发布、版本
校验和旧 MCP 名称是否删除，要根据实际调用日志单独决定，不能随 UI 合并一起删除。

## 9. 暂不修改的内容

为保证稳定性，本方案暂不做以下事情：

- 不把地图专用图片任务改成普通图片请求；
- 不把资源管理器的任意目录能力收回或限制到项目根；
- 不让外部目录文件自动成为游戏工程资源；
- 不新增一套图片尺寸、文件大小或供应商参数硬限制；
- 不删除现有地图版本、候选发布、原子保存、撤销和冲突保护；
- 不把 AI 的提案和应用合并成无确认的直接文件写入；
- 不一次性重命名所有旧 MCP 工具或删除旧 URL；
- 不修改救援窗口 `4321`，不触碰发布和部署流程；
- 不在本轮执行功能实现、全量测试、提交、推送或部署。

## 10. 验收清单

### 入口

- 工具箱一级只看到资源管理器、游戏工作区、图片工作室和浏览器预览；
- 在任意已授权的空目录创建新游戏工程，不依赖固定路径；
- 新建工程完成后存在有效 `.tiled-project`、初始地图和可解释的地图模式；
- 向导中的地图模式、尺寸和目录只是预设，进入工程后可以修改，不存在因预设导致的永久锁定；
- 创建时设置的工程名称显示在“我的游戏工作区”，可以同时保留多个工程；
- 创建完成后能按工程名称从“我的游戏工作区”重新打开该工程并恢复上次已保存环境；
- 同名工程仍能通过 `projectId` 和位置摘要准确区分；
- 地图、World、瓦片集、角色不再各自占用一级入口；
- 从工具箱、资源管理器和角色编辑器打开图片时使用同一个图片工作室；
- 地图图片候选在地图工作区内可见，并明确显示“候选”和“发布”两个阶段。

### 上下文

- 新建工程完成后自动进入新工程，工程文件不再是 `null`；
- 从工程列表恢复时按 `projectId` 重新建立会话，不依赖固定路径或其他工程的缓存状态；
- 缓存过期或工程被移动时不会静默加载其他工程，且能保留入口供重新定位；
- 打开工程 A 后所有子编辑器都显示工程 A，不能被 localStorage 记忆的工程 B 覆盖；
- 地图、World、瓦片集和角色显示的资源路径均是当前工程相对路径；
- 一个对话可以解除工程 A 后绑定工程 B，绑定状态和 AI 工具范围同步切换；
- 对话未绑定工程时，游戏 AI 读取工具仍可使用当前用户有权限的只读工程上下文；修改工具不生效，也不会使用上一次工程的写入上下文；
- 切换工程或账号后旧窗口不能读取或写入新工程；
- 关闭有未保存修改的工作区时有明确处理，恢复列表不宣称恢复未保存内容；
- 同一对话的多个窗口不会分别指向不同工程；需要同时打开多个工程时使用不同对话；
- 从未绑定对话打开已绑定工程时，右侧 AI 小窗显示工程原绑定对话，而不是打开来源对话；
- 工程无绑定时，右侧 AI 小窗只显示绑定入口，不生成无归属对话；
- 资源管理器切到任意外部目录后不会出现可把该目录伪装成游戏工程的专业入口；
- 图片工作室的源图、输出位置和当前工程显示一致。

### AI

- 模型能区分当前地图窗口协作、已授权工程协作和图片操作；
- 同义的 `get_map_context` 和 `propose_tiled_patch` 不再以无范围描述重复出现；
- `propose` 不会写入，`apply` 有明确授权、版本和候选边界；
- AI 不能通过绝对路径或参数切换到任意工程；
- 地图图片候选仍能绑定地图版本，并能发布到图片层、瓦片对象或瓦片集；
- 图片供应商返回尺寸与请求不同不会导致结果被工具层无条件丢弃。

## 12. 最终执行方案

### 12.1 用户看到的最终入口

```text
工具箱
├── 我的游戏工程
│   ├── 已创建的工程名称 A
│   ├── 已创建的工程名称 B
│   ├── 新建游戏工程
│   └── 添加已有工程
├── 资源管理器
├── 图片工作室
└── 浏览器预览
```

“新建游戏工程”负责创建完整工程骨架；“添加已有工程”负责把已经存在的工程登记进列表。地图、World、瓦片集、角色和
地图素材不再作为工具箱一级卡片，而是当前游戏工程里的编辑能力。

### 12.2 新建流程

1. 用户选择任意已授权目录并填写游戏工程名称；名称是可修改的显示名称，不是路径和唯一键。
2. 用户选择一个初始地图预设。默认是“瓦片 + 建筑对象”的建筑/经营结构，也可以选择“背景图 + 对象”结构。
3. 用户确认地图方向、尺寸、瓦片尺寸、初始图片或瓦片集等参数。它们只决定初始文件，不成为工程永久限制。
4. 服务端在临时位置生成 `.tiled-project`、初始地图和资源目录，完成格式与引用校验后一次性写入目标目录。
5. 创建成功后生成 `projectId`、工程注册表记录、第一份工作区快照和 `projectContext`，并自动进入游戏工作区。

建筑/经营预设应初始包含 Ground 瓦片层、Buildings 对象层、Collision 对象层和 Events 对象层，必要时附带 Background
图片层。没有首个瓦片集时必须明确显示“瓦片工具待配置”，不能把禁用状态伪装成加载故障；用户随后可以添加或更换瓦片集。
这只是初始结构，不限制以后增加、删除或改用其他层。

### 12.3 多工程和恢复

- WFL 持久保存多个工程注册表项，不设置只能有一个当前工程的规则；
- 列表项显示用户设置的名称、最近打开资源、状态和位置摘要；
- 点击名称只提交 `projectId`，服务端检查路径和权限后重新建立会话；
- 工作区快照恢复上次已保存的地图、标签、编辑器、缩放、视口和面板状态；
- 工程索引缓存只用于加速资源树和摘要，按指纹/修改时间失效后重新读取磁盘；
- 缓存或快照失效不能导致静默跳转到其他工程；
- 移除列表项不删除工程文件，工程移动时提供重新定位；
- 一个对话同一时间只绑定一个工程；从工程 A 打开工程 B 时先处理未保存修改，再解除 A 并绑定 B；
- 切换工程后，主站向 AI 标记当前绑定已变化，后续修改工具只能作用于 B；读取工具仍可按用户权限使用其他工程的只读上下文，不能借读取参数获得写入权限；
- 对话解绑后，游戏 AI 读取工具仍可使用用户有权限的工程，但该对话的修改工具暂时不可用；人工查看、人工操作和原对话聊天仍可用；
- 一个工程同一时间只允许一个对话持有 AI 修改绑定，其他有权限的对话和窗口仍可人工查看、人工操作并使用 AI 读取能力；
- 同一对话的多个窗口共享同一个绑定 AI 小窗，需要同时使用多个工程时使用多个对话；
- 从任意窗口打开已绑定工程时，右侧显示绑定对话；没有绑定时显示“绑定当前对话”，不创建临时 AI 对话；
- 绑定切换只改变 AI 读取和修改权限，不删除文件、不禁用原对话，也不阻止原对话继续聊天或人工查看工程。

### 12.4 工具和 AI 迁移

实现顺序固定为：

1. 先实现工程注册表、`projectId`、单对话单工程绑定、`projectContext` 和服务端会话恢复；
2. 再实现新建/添加/打开工程向导和工作区快照，创建工程时绑定当前对话；
3. 再合并工具箱入口，把专业编辑器改为消费上下文，并支持解除绑定后切换工程；
4. 再让图片工作室和地图素材候选共用上下文，但保留各自后端事务；
5. 最后整理 AI MCP 的范围描述、同义工具和授权上下文，确保读取工具使用有权限的只读上下文，修改工具只使用 active binding。

AI 永远不能从名称、路径、缓存或“当前项目”猜工程。它只能操作当前授权的工程上下文；通用文件管理器可以有自己的
任意目录能力，但不能把这个能力隐式升级为游戏编辑或 AI 工程写入能力。

### 12.5 必须验证的最小场景

- 在两个不同的任意目录分别新建工程，名称和工作区状态可以同时保留；
- 关闭后从工程名称列表分别恢复两个工程，资源、标签和写入目标不串；
- 在同一对话中解除工程 A、绑定工程 B，再解除 B、重新绑定 A，绑定、资源和写入目标都正确；
- 同一对话在两个窗口打开时共享同一工程，不会分别指向工程 A、B；
- 使用两个对话分别绑定工程 A、B 时，AI 工具调用和资源写入互不跨越；
- 使用两个对话查看同一工程时都能读取，但只有一个对话可以修改；
- 修改绑定转移后，原对话仍能读取和聊天，新对话获得修改能力；
- 从工程 A 已绑定对话 B 的任意窗口进入编辑器时，右侧 AI 小窗始终显示 B；
- 解除 B 并绑定当前对话 A 后，所有该工程编辑器窗口的 AI 小窗同步显示 A；
- 主站与右侧小窗使用同一个 `threadId`：双方都能看到完整历史、附件引用、上下文管理状态、compaction item、工具调用和工具结果，不能各自截取或拼接一份上文；
- 主站发送的消息在小窗出现，小窗发送的消息在主站出现，刷新、重连或多窗口订阅不会重复消息、重复提交或丢失增量事件；
- 主站或小窗发送停止命令都能停止同一个长任务；任务进行中、已完成、已取消和失败状态在两处一致，恢复后沿用服务端状态；
- 从外层对话 X 打开绑定对话 Y 的工程时，小窗显示 Y 的完整上下文，外层主站仍显示 X，不能串用或覆盖；
- 切换工程时存在未保存修改会先要求处理，不会把 A 的修改写入 B；
- 修改预设创建的地图设置、层和资源后，编辑器仍按实际文件工作；
- 外部文件管理目录不会被误当作游戏工程；
- 没有 `.tiled-project` 的旧工程通过“添加已有工程”得到明确的兼容状态或显式补齐流程；
- 地图对象编辑、地图版本保存、地图图片候选发布继续正常；
- AI 读取可以使用当前用户有权限的任意工程只读上下文；AI 修改只能使用绑定工程上下文，任何工具都不能通过参数切换服务端路径；
- 测试服务使用自己的临时项目根和登录会话，不继承生产环境的 `CODEX_DESKTOP_PROJECT_ROOTS=/srv`，也不写入真实工程。

本方案的第一批编码目标是工程注册表、通用新建向导、工程列表恢复和上下文传递；在这四项稳定前，不先大规模删除旧
编辑器页面或重写地图/图片后端。
