# Goal 任务终止与生命周期

本文记录 Goal 和普通 Codex 回合的终止边界，避免把“安全暂停 Goal”和“立即终止当前任务”混成一个操作。

## 立即终止的语义

用户点击“立即终止”后，服务端按以下顺序处理：

1. 读取本地任务权威快照并校验 Thread、Turn 身份。
2. 立即把任务状态标为 `stopping`，让所有浏览器窗口马上看到终止中。
3. 并行启动 Goal 的原生状态读取和人工暂停记录。
4. 立即向 Codex App Server 发送 `turn/interrupt`，不等待 Goal 读取、Goal 写入或当前 Turn 自然完成。
5. 收到 `turn/completed` 后再把 Goal 的恢复侧车从 `pausing` 收口为 `paused`。

因此，几个小时的运行任务不会因为 Goal 的暂停写入而继续运行几个小时。`turn/interrupt` 的含义是中断当前 Turn，不是等待当前 Turn 完成。

## 异常与隔离

- 原生中断失败时，系统按任务所在项目定向重试；只有没有其他项目任务时才允许重启共享 App Server，避免误伤其他对话。
- 备用窗口使用独立的进程组恢复路径，但本文件不授权修改、重启或升级冻结的 `4321` 组件。
- 清除 Goal 是幂等操作：成功响应丢失时会复读原生 Goal；确认已清除后，同时删除恢复定时器、额度复核和任务中心缓存。
- 迟到的 Goal 通知不能替代已清除状态；浏览器会使旧请求失效并删除本地 Goal 快照。

## 验收标准

- 终止请求先到达 `turn/interrupt`，而不是先等待 `thread/goal/get` 或 `thread/goal/set`。
- 任务中心和主窗口先显示 `stopping`，最终显示 `interrupted` 或明确的恢复状态。
- 直接终止带 Goal 的任务后，原生 Goal 为 `paused`，且可以人工继续。
- 清除后 `thread/goal/get` 返回空，任务中心不再保留该 Goal。
- 一个项目的中断失败不重启共享 Bridge，也不改变其他项目的任务。

## 2026-08-14 一致性修复计划（当前 Goal）

本轮把“点击终止后提示已清理，但原生任务仍在运行”列为 P0。服务端不能只依赖
进程内 `TaskStatusTracker`：该表在重连、事件丢失或后端切换后可能没有当前 Turn。

固定处理顺序：

1. 本地快照能确认 Thread/Turn 一致时，立即发送 `turn/interrupt`；
2. 本地快照缺失或 ID 不一致时，先查询原生 `thread/turns/list`，找到真实活动 Turn 后再发送中断；
3. `thread/turns/list` 没有活动项仍不够：必须用 `thread/read(includeTurns=true)` 找到请求 Turn 的明确终态，或获得完整且全部为终态的 Turn 快照；空页、空 turns、仅 `idle/notLoaded`、`no rollout found` 都不能作为任务结束证据；
4. 原生状态无法确认时返回错误，前端不得显示“已清理”；
5. 中断成功后继续由 `turn/completed`、有界对账和 watchdog 完成最终收口，任务中心与主窗口都使用同一权威状态；
6. Goal 清除成功响应返回前必须复读 `thread/goal/get` 确认为空。确认后服务端和浏览器各自建立清除墓碑，迟到的 `thread/goal/updated` 不得复活 Goal；新的显式 Goal 设置会开启新一代状态。

实现验收：

- 本地任务表为空但原生 Turn 活跃时，点击终止仍能中断原生 Turn；
- 本地显示“遗留状态已清理”前，原生列表已经确认无活动 Turn；
- Goal 清除后，服务端 `thread/goal/get`、`/api/task/center`、WebSocket 和浏览器任务胶囊不再恢复为运行中；
- 同一对话重新保存新 Goal 后，旧墓碑解除，新 Goal 能正常显示和继续；
- 终止和清除操作均保持幂等，不因迟到通知重复创建恢复定时器或任务。

## 本轮已加固与仍待验收

已加入聚焦回归：空 `turns/list` 但原生仍有活动 Turn、空完整快照且 Thread 仅显示 `idle`、Goal 终态收到较旧的迟到更新、同一终态 Turn 重放 `turn/started`。这些情况现在必须保持运行/终态一致，不能返回“遗留状态已清理”假成功。

同时，旧 Turn 的迟到 `turn/completed` 不再清理新 Turn 的写租约或审批请求，浏览器也不会为中断、失败或旧 Turn 弹出“任务已完成”。仍待候选环境验证的项目是多项目并发下的真实供应商终止、`thread/read` 传输失败后的手动恢复，以及多窗口重复点击终止的完整浏览器回归。

## 2026-08-14 追加竞态修复（0.43.54-beta）

状态机额外固定三条终止围栏：

- `stopping` 期间迟到或重放的不同 Turn 不得覆盖正在终止的 Turn ID；旧 Turn 的终态仍必须能够收口任务；
- 已识别 Turn 的任务收到延迟 `thread/closed` 时不得提前变成 `completed`；
- 中断期间发生投递不确定时保留 `stopping`，不能降级为会让 watchdog 停止工作的 `uncertain`。

本轮的“已清理”提示只有在原生确认和本地任务快照都不再活跃时才允许出现。0.43.54-beta 的剩余验收仍是候选环境的多项目并发真实终止、`thread/read` 传输失败恢复和多窗口重复终止浏览器回归。

发布侧同样采用有界探测：Git、系统能力和候选校验不能无限等待；达到探测超时后只记录发布失败并保留原活动后端，不得把未确认的状态报告为已部署。
Claude 轻量兼容探测也必须在成功和超时两条路径回收 CLI 子进程，不能因遗留子进程让候选发布停在 testing。

## 2026-08-14 追加 Goal 终止确认修复计划（0.43.55-beta）

用户反馈表明，0.43.54-beta 仍存在一条实际竞态：当前 Turn 已被原生端判定为无活动时，终止接口会吞掉暂停 Goal 的异常，直接返回“遗留状态已清理”；如果 Goal 仍是 `active`，Codex 会马上开启下一轮，任务中心随后又显示运行中。

本批次固定以下契约：

1. “当前 Turn 已结束”和“Goal 已停止继续运行”是两个独立条件，不能只确认前者。
2. 终止流程读取 Goal 必须使用原生 Thread ID，支持迁移/映射对话。
3. Goal 存在时，必须收到 Goal 非 `active` 的原生复读结果；暂停侧车失败、读取超时或状态不确定时，响应只能标记未确认，禁止返回清理成功。
4. 只有 `confirmedInactive === true`、`nativeVerified === true`、返回任务快照非活跃且 `goalPauseConfirmed === true` 时，浏览器才能显示“遗留状态已清理”。
5. 当前 Turn 已结束但 Goal 暂停未确认时，浏览器清除当前 Turn 的旧身份，保留 Goal 的运行状态并提示“正在刷新实际状态”，不能把它伪装成已清理。
6. 正常终止仍先并行发送原生 `turn/interrupt`，Goal 暂停确认不得阻塞原生中断；确认失败只影响成功提示和后续状态，不等待 Turn 自然运行结束。

验收项：

- Goal 为 `active`、当前 Turn 已结束但暂停请求失败时，不出现“遗留状态已清理”；
- Goal 为 `active` 且暂停确认成功时，终止后不会自动开启下一轮；
- 无 Goal、已暂停 Goal、完成 Goal 仍可正常终止当前 Turn；
- 映射/迁移 Thread 使用原生 ID 读取和复核 Goal；
- 重复点击终止、多窗口刷新、迟到 `turn/started` 与 `thread/goal/updated` 不得把已确认暂停的 Goal 恢复为运行中；
- 服务端、任务中心和主对话使用同一个 `goalPauseConfirmed` 契约，失败状态可重试且不误报。

## 2026-08-14 0.43.55-beta 实施记录

- 终止前和终止后的 Goal 复核均只接受明确的 `paused`、终态或无 Goal；未知状态、读取失败和延迟快照一律保持未确认。
- Goal 暂停超时后，原生 Turn 中断完成后只做一次有界复核/重试；原生中断不被 Goal 侧车请求阻塞。
- Goal 写入、清除和恢复统一将公开 Thread 映射到原生 Thread；原生迟到 Goal 通知在进入恢复侧车前也会反向映射，避免迁移对话产生幽灵 Goal。
- 新增暂停失败回归：服务端必须返回 `goalPauseConfirmed: false`，任务中心和主窗口不得显示“遗留状态已清理”。
- Goal 暂停/清除确认改为有界退避轮询，并要求连续两次原生快照一致；一次瞬时的空或非活动快照不能触发清理成功。
- `turn/interrupt` 收到原生确认后只做短暂终态核对并返回权威任务快照；核对未完成时返回待核实标记，后台 watchdog 和终态对账继续运行，前端不得提前清除当前 Turn。
- 主窗口和任务中心统一使用 `confirmedInactive + nativeVerified + taskStatus 非活动 + goalPauseConfirmed` 四项条件显示清理成功；Goal 复核进行中只提示“正在核实”。
- 本批次目标是完成聚焦回归后递增至 `0.43.55-beta`，按蓝绿强制切换发布；物理输入设备、大规模性能和 4321 救援组件仍不在本批次范围内。

## 2026-08-14 0.43.55-beta 追加根治记录：原生终态必须独立取证

聚焦复现发现，单纯收到本地 `turn/completed` 通知仍可能早于原生 Turn/命令后代真正停止。
因此本轮继续收紧“遗留状态已清理”的证据链：

- [x] `waitForNativeInterruptSettlement()` 不再把本地终态通知直接当作 `nativeVerified`；每次成功都必须由原生 `thread/turns/list` 或 `thread/read(includeTurns=true)` 给出对应 Turn 的明确终态。
- [x] 原生 Turn 仍为活动态而本地任务已经终态时，重新建立本地 `stopping` 围栏，避免状态胶囊显示完成、终止按钮失去任务身份或 watchdog 停止重试。
- [x] 主窗口和任务中心额外拒绝历史/兼容服务返回的 `notification-terminal` 证据，防止旧前端把本地通知误报为原生清理完成。
- [x] 增加集成回归：Goal 运行中先发送伪终态本地通知，第一次原生中断 ACK 不真正停止时不得提示清理成功；第二次真实原生终态后才允许确认。
- [x] 候选打包的 Git、tar 和备份子进程改为监听 `close`、有界超时和 SIGTERM→SIGKILL 进程组收口；异常退出后仍执行临时 worktree 清理，并保留旧备份对。

本修复不改变“立即发送 `turn/interrupt`”原则，也不等待任务自然完成。无法取得独立原生证据时，界面只显示“正在核实/终止请求已送达”，绝不显示“遗留状态已清理”。

## 2026-08-14 追加验收计划：终止按钮与真实清除必须同一状态

用户再次复现“Goal 对话点击终止后提示已清除，但任务中心和原生任务仍显示运行中”。这不是提示文字问题，而是终止请求的最终事务没有完成，前端却把某个中间响应当成清除成功。本项加入长期更新计划，优先级 P0：

- 点击终止的同步响应只能表示 `stopRequested`，不能表示 `cleared`；前端立即进入 `stopping`，保留当前 Thread/Turn 身份和再次终止/刷新入口。
- 服务端必须先对当前 Turn 发出原生 `turn/interrupt`，再异步收口 Goal 暂停、任务快照和恢复侧车；任何 Goal 读取、写入或清除请求都不能阻塞这条中断路径。
- 只有原生 Turn 已取得明确终态、Goal 已取得明确非活动状态、任务中心快照已落盘为非活动，并且清除墓碑已写入后，才允许返回或显示“遗留状态已清理”。
- 清除事务任一阶段超时、断线、返回未知状态或回执丢失时，必须保持 `stopping`/`needs_reconcile`，不能显示成功；下一次刷新、重连或人工点击“重新核实”应继续同一个操作，而不是新建重复任务。
- “清除遗留任务”必须同时验证本地运行记录、原生 Turn、Goal 恢复记录、任务中心和浏览器状态；只删除浏览器缓存或只删除本地任务记录都不算完成。
- 终止按钮的 watchdog 必须有界重试并可取消；任务确实停止后立即释放按钮对应的 Turn 租约，任务持续运行时不能释放身份让 UI 失去控制权。

新增验收场景：

1. 原生 Turn 仍为 `inProgress` 时伪造本地 `completed`，终止响应不得显示清除成功，且任务中心保持 `stopping`。
2. 原生中断 ACK 已返回但 `thread/read` 仍无明确终态，页面刷新后仍显示“正在核实”，不能恢复为运行中或清除成功。
3. Goal 清除回执丢失、服务端重启、双窗口重复点击后，恢复同一个清除事务；最终原生 Goal、服务端任务中心和浏览器均为非活动。
4. 一个长时间运行任务点击终止后，立即可观察到 `stopping`，不会等待任务自然完成；但“已清理”必须等待真实终态证据。
